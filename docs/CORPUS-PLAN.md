# Apex Recipes compatibility implementation plan

This plan concerns the unchanged official revision `b364267fc786a8a3ac4c3968467fcc4abd4adac6`. All 322 tests remain in every corpus run. The native first blocker is only the first unsupported operation reached; it does not describe the rest of a test's requirements. The generated feature matrix includes those later dependencies and their source locations.

## Configuration that is genuinely external to Apex source

`corpus/apex-recipes.environment.json` declares the local fixture and provenance. `config/project-scratch-def.json` supplies Developer edition, US/en_US, PlatformCache/Walkthroughs/EnableSetPasswordInApi features and Lightning settings. `README.md` installs `Apex_Recipes` and the platform-provided `Walkthroughs` permission sets, imports both data plans, and runs `data/setup.apex`. These are configuration inputs, not permission to deploy or run arbitrary upstream shell scripts.

The repository includes 9 permission-set XML files, 1 permission-set-group XML file, 11 custom-metadata records, 1 cache-partition file, custom-object/field metadata, static resources, and DataWeave source. These should be loaded rather than replaced with hardcoded rows. `ApexClass`/source catalog records can be derived from the actual project. `DataFactoryForPackageInstalls` and `data/setup.apex` must execute ordinary supported Apex if a SeeAllData baseline needs their business data.

Standard `Profile` definitions are absent. `TestFactory` queries **Minimum Access - Salesforce** and **Marketing User**; `SOQLRecipes_Tests` also requests **Standard User**. The fixture's current user references **System Administrator**. Identity rows alone cannot establish their Salesforce CRUD/FLS masks. The environment file now explicitly configures synthetic local personas by ProfileId: minimum access starts with no grants; the administrator receives schema-capped grants; standard and marketing personas receive business-object read/create/edit grants without delete; the marketing persona omits Account.TradeStyle field grants. These are local assumptions, not inferred Salesforce defaults. A versioned, independently verified baseline or explicit org export is still required for claims about real default-profile parity. `Walkthroughs` is referenced by installation instructions but its permission-set definition is not in the repository.

Effective grants combine profile policy, assigned permission sets and calculated groups, then intersect with schema capabilities. A false flag is absence of a grant, so another assigned permission set may grant it. Id, audit, formula and auto-number fields remain read-only regardless of permission grants. Unknown object classification, field permissionability or row-sharing behavior remains blocked. `runAs` changes user/sharing context; it must not by itself turn ordinary system-mode Apex DML into user-mode DML. Explicit USER_MODE and `stripInaccessible` use the computed permissions.

The exact security assertions justify keeping these layers separate. `CanTheUser_Tests` checks Account CRUD, accessible Name/Id, non-updateable Id and nonexistent fields. `Safely_Tests` creates PermissionSet/ObjectPermissions rows at runtime, verifies minimum-user access changes, strips TradeStyle, and denies marketing-persona Case deletion. `StripInaccessibleRecipes_Tests` imports actual permission sets to retain Campaign.ActualCost while removing BudgetedCost, strips Contact fields and child records, and expects removed queried fields to behave as unselected fields rather than present null values. These exercise general schema/policy/projection semantics, not named-test exceptions.

Organization identity, instance, timezone, fiscal year, UI theme, current user, currency features and clock need a declared local context. The proposed fixture labels synthetic choices separately from values inherited from upstream; it does not claim they describe a real org. `OrgShape_Tests` often compares queried Organization data with UserInfo/helper output, so all views must share one underlying state.

Only two methods use `SeeAllData=true`: `OrgShape_Tests.testPlatformCacheDisabledWhenSeeAllDataTrue` and `OrgShape_Tests.testSeeAllDataPositiveWhenEnabled`. Honor the annotation with normal transaction/visibility semantics. Do not skip them, silently turn it off, or expose arbitrary host data. An offline explicit baseline can supply their environment without a live org connection.

The cache partition metadata sets `isDefaultPartition` to **false**. Preserve that value. The test comments mention manually selecting a default partition, while `OrgShape.getAvailableOrgCachePartition()` actually queries an available unnamespaced partition. Model the actual metadata/API behavior and let a missing prerequisite produce a configuration diagnostic; do not change metadata to force a test result.

## Tests that are weaker evidence

Some upstream methods verify only nonthrowing execution or contain no active domain assertion. `PSGAdvancedTestingRecipes.testNegativePSGTestsWithMetadata` is an example scaffold: its example business-code body is empty and its final assertion is commented out. A pass is still reported and conserved, but cannot substantiate security correctness. The corpus runner marks negative checks that use an entry sentinel rather than an inverted original assertion. Domain-level negative fixtures and platform conformance tests remain necessary for these families.

The corpus is a useful compatibility workload, not a complete Salesforce semantic specification. Even 322/322 local passes with all negative checks killed must retain experimental assurance until compared against independent Salesforce results and broader conformance fixtures.
